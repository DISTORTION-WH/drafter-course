# Глава 4. Сеть, домен и HTTPS

## Результат главы

Вы разберётесь, почему база данных не должна быть видна из интернета, создадите сетевые границы приложения и подготовите адрес вида `api.example.com` с HTTPS.

## 1. Минимальная модель сети

VPC — это ваша частная сеть в AWS. В ней есть подсети:

- публичные — имеют маршрут к Internet Gateway;
- приватные — не принимают прямые входящие подключения из интернета;
- изолированные — не имеют прямого маршрута наружу.

Для стандартного production-профиля используйте минимум две Availability Zone:

```text
Internet
   |
Application Load Balancer — public subnets, AZ-a/AZ-b
   |
ECS API and worker — private subnets, AZ-a/AZ-b
   |
RDS PostgreSQL — isolated/private DB subnets, AZ-a/AZ-b
```

Так отказ одной зоны не обязан остановить всё приложение.

## 2. CIDR простыми словами

CIDR задаёт диапазон внутренних IP-адресов. Например, `10.20.0.0/16` оставляет достаточно места для подсетей. Вам не надо вычислять адреса вручную: CDK умеет распределить их, но диапазон нельзя выбирать случайно, если позже сеть будет соединяться с другой VPC или корпоративной сетью.

Запишите решение в ADR:

```md
# ADR: диапазон VPC

- CIDR: 10.20.0.0/16
- Регион: выбранный в главе 1
- AZ: 2
- Причина: отдельный диапазон для production, без пересечения со staging
```

## 3. NAT Gateway и цена

Контейнер в приватной подсети часто должен обратиться к провайдеру данных, ECR, CloudWatch или Secrets Manager. Для исходящего доступа обычно применяют NAT Gateway. Он оплачивается за время работы и обработанный трафик.

Для учебного staging возможны компромиссы:

- одна NAT Gateway вместо одной на каждую AZ;
- публичный IP у ограниченного сервиса без входящих правил;
- VPC endpoints для AWS-сервисов.

Это не универсальные «лучшие практики». Сравните надёжность, цену и сложность в AWS Pricing Calculator. В production с требованиями высокой доступности обычно NAT размещают по зонам. Не копируйте дорогую схему, не посчитав бюджет.

## 4. Security Group — сетевой пропуск

Security Group разрешает только перечисленные соединения. Начните с запрета всего лишнего:

| Компонент | Входящие соединения | Исходящие соединения |
|---|---|---|
| ALB | TCP 443 от интернета; TCP 80 только для redirect | порт API в ECS |
| API | порт приложения только от SG балансировщика | PostgreSQL, Redis, HTTPS наружу |
| worker | входящих нет | PostgreSQL, Redis, HTTPS наружу |
| RDS | TCP 5432 только от SG API/worker/migration | обычно ничего дополнительного |
| Redis | порт Redis только от SG API/worker | по необходимости |

Не разрешайте `0.0.0.0/0` на PostgreSQL, Redis, SSH или внутреннем порту приложения. Для ECS Fargate SSH вообще не требуется.

В CDK связывайте группы ссылками, а не IP-адресами:

```ts
database.connections.allowDefaultPortFrom(apiService.service);
database.connections.allowDefaultPortFrom(workerService.service);
```

Смысл строки: AWS разрешит трафик к стандартному порту базы только задачам указанных сервисов.

## 5. Load Balancer и health check

Application Load Balancer принимает HTTPS и передаёт запрос здоровой ECS-задаче. API должен иметь отдельную ручку:

```text
GET /health/live   — процесс запущен
GET /health/ready  — процесс способен обслуживать запрос
```

`live` не должен ходить в базу. `ready` может проверять критические зависимости с коротким тайм-аутом. Не возвращайте ключи, строки подключения или подробные исключения.

Настройте:

- listener 443 с сертификатом ACM;
- listener 80 только с перенаправлением на 443;
- health check `/health/ready`;
- deregistration delay и graceful shutdown;
- idle timeout, подходящий API;
- access logs в S3, если они входят в вашу политику хранения данных.

## 6. Домен, Route 53 и ACM

Последовательность:

1. Зарегистрируйте домен у выбранного регистратора.
2. Создайте hosted zone в Route 53 либо настройте DNS у текущего регистратора.
3. Закажите публичный сертификат ACM для `api.example.com`.
4. Подтвердите владение через DNS.
5. Привяжите сертификат к HTTPS listener ALB.
6. Создайте A/AAAA Alias-запись `api.example.com` на ALB.

Сертификат для ALB должен находиться в том же регионе, что и ALB. Для CloudFront сертификат обычно создают в `us-east-1`; это отдельный случай, который будет в главе 7.

## 7. Безопасный DNS cutover

До переключения production:

- уменьшите TTL заранее;
- проверьте staging-домен;
- убедитесь, что мобильная сборка получает URL API из production-конфигурации;
- сохраните предыдущую запись и план возврата;
- не удаляйте старое окружение до завершения smoke-тестов.

Проверки после переключения:

```bash
curl -i https://api.example.com/health/live
curl -i https://api.example.com/health/ready
```

Проверьте также сертификат, редирект с HTTP, CORS, авторизацию и запрос с физического телефона.

## Практика

1. Нарисуйте VPC с двумя AZ и всеми потоками трафика.
2. Создайте таблицу Security Group без правила `0.0.0.0/0` для внутренних ресурсов.
3. Поднимите staging ALB и HTTPS-домен.
4. Докажите, что RDS недоступна с домашнего компьютера, но доступна migration task.
5. Сохраните команды smoke-теста в `docs/runbooks/dns-cutover.md`.

## Готово, если

- API доступен только по HTTPS;
- HTTP перенаправляется на HTTPS;
- база и worker не имеют публичного входа;
- правила сети объяснимы одной таблицей;
- есть проверенный план DNS-отката.
