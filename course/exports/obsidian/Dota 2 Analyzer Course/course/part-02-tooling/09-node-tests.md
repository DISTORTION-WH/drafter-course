# Глава 9. Первые автоматические тесты

## 1. Зачем нужны тесты

Ручная проверка `console.log` отвечает только на текущий запуск. После изменения формулы нужно снова помнить все случаи и сравнивать вывод.

Автоматический тест:

- задаёт вход;
- запускает функцию;
- сравнивает результат с ожиданием;
- завершается ошибкой при несовпадении;
- повторяется одной командой.

## 2. Встроенный test runner Node.js

Первая версия проекта использует встроенные модули:

```js
import test from "node:test";
import assert from "node:assert/strict";
```

Внешняя dependency пока не нужна.

Script:

```json
"test": "node --test"
```

Запуск:

```powershell
npm test
```

## 3. Первый тест

`test/calculations.test.js`:

```js
import test from "node:test";
import assert from "node:assert/strict";

import { calculateKda } from "../src/domain/calculations.js";

test("calculateKda рассчитывает обычный случай", () => {
  const actual = calculateKda(10, 2, 8);
  const expected = 9;

  assert.equal(actual, expected);
});
```

## 4. Arrange, Act, Assert

Структура теста:

```text
Arrange — подготовить вход и ожидание
Act     — выполнить функцию
Assert  — сравнить результат
```

В маленьком тесте эти части могут занимать по одной строке.

## 5. Имя теста

Плохо:

```js
test("test 1", ...)
```

Хорошо:

```js
test("calculateKda использует единицу как делитель при нуле смертей", ...)
```

При падении имя должно объяснить нарушенное правило.

## 6. Граничный случай

```js
test("calculateKda не возвращает Infinity при нуле смертей", () => {
  const actual = calculateKda(5, 0, 5);

  assert.equal(actual, 10);
  assert.equal(Number.isFinite(actual), true);
});
```

## 7. Сравнение объектов

Для структур используйте deep equality:

```js
assert.deepEqual(actual, expected);
```

`assert.equal` сравнивает ссылки объектов, поэтому два отдельных одинаковых объекта через него не равны.

## 8. Проверка ошибки

```js
assert.throws(
  () => analyzePlayer(invalidPlayer),
  /kills должен быть неотрицательным числом/,
);
```

Тест проверяет и сам факт ошибки, и полезную часть сообщения.

## 9. Проверка неизменности входа

```js
test("analyzePlayer не изменяет исходный объект", () => {
  const player = {
    name: "North",
    hero: "Juggernaut",
    team: "radiant",
    kills: 12,
    deaths: 2,
    assists: 9,
  };

  const originalCopy = { ...player };

  analyzePlayer(player);

  assert.deepEqual(player, originalCopy);
  assert.equal(player.kda, undefined);
});
```

## 10. Test fixture

Fixture — заранее подготовленные данные для теста.

Большой объект можно создавать функцией:

```js
function createValidPlayer(overrides = {}) {
  return {
    name: "North",
    hero: "Juggernaut",
    team: "radiant",
    kills: 12,
    deaths: 2,
    assists: 9,
    ...overrides,
  };
}
```

Тест отрицательных kills:

```js
const player = createValidPlayer({ kills: -1 });
```

Каждый тест получает новый объект и не зависит от изменений другого теста.

## 11. Один тест — одно бизнес-правило

Не собирайте двадцать несвязанных проверок под именем «всё работает». При падении будет непонятно, что сломано.

Допустимо несколько assertions, если они описывают один результат, например полную team summary.

## 12. Детерминированность

Тест должен давать одинаковый результат при одинаковом коде.

Источники нестабильности:

- текущее время;
- случайные числа;
- реальный внешний API;
- порядок общего изменяемого массива;
- timezone;
- сеть.

Unit tests не вызывают OpenDota. Позже provider tests используют сохранённые fixtures и отдельные integration checks.

## 13. Не тестируйте внутреннюю реализацию без необходимости

Тестируйте публичное поведение:

```text
вход → результат/ошибка
```

Если внутренняя функция не экспортируется, обычно не нужно экспортировать её только ради теста. Проверьте результат через публичную функцию.

## 14. Красный, зелёный, улучшение

Полезный цикл:

1. Написать тест, который падает.
2. Убедиться, что он падает по ожидаемой причине.
3. Реализовать минимальное исправление.
4. Увидеть зелёный тест.
5. Улучшить код, сохраняя зелёные тесты.

Тест, который никогда не был замечен падающим, может проверять не то условие.

## 15. Что означает падение

Падение теста не всегда означает ошибку production-кода. Возможны:

- неправильное новое поведение;
- устаревшее ожидание теста;
- ошибка fixture;
- неправильная environment configuration.

Не меняйте expected только ради зелёного статуса. Сначала решите, какое бизнес-правило правильное.

## Definition of Done

- `npm test` запускает тесты.
- Вы понимаете Arrange, Act, Assert.
- У каждого теста информативное имя.
- Есть обычные и граничные случаи.
- Вы проверяете ошибки через `assert.throws`.
- Вы умеете сравнить объекты через `deepEqual`.
- Вы не обращаетесь к реальному внешнему API из unit test.
