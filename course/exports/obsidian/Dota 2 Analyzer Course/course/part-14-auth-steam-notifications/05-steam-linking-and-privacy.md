# Глава 5. Steam linking и приватность

## 1. Authentication и profile enrichment — разные операции

OpenID доказывает контроль Steam identity. Получение display name, avatar или игровой статистики — отдельный provider-запрос с собственной доступностью и правилами.

```text
OpenID verification -> подтверждённый SteamID64
Steam Web API        -> необязательные публичные профильные данные
матчевые providers   -> отдельные данные матчей
```

Вход не должен падать только потому, что дополнительный profile API временно недоступен. Создайте пользователя по подтверждённому SteamID, а enrichment выполните асинхронно.

## 2. Не храните лишнее

Минимум для identity:

- внутренний user UUID;
- SteamID64;
- время подтверждения;
- технические timestamps.

Опциональный кэш публичного профиля:

```sql
CREATE TABLE steam_profile_cache (
  steam_id text PRIMARY KEY REFERENCES steam_links(steam_id),
  display_name text,
  avatar_url text,
  visibility_state text,
  fetched_at timestamptz NOT NULL,
  expires_at timestamptz NOT NULL
);
```

Display name нельзя использовать для уникальности, авторизации или URL ownership. Пользователь способен его поменять.

## 3. Первый вход и linking существующего пользователя

Есть два разных сценария:

### Login with Steam

Если SteamID уже связан, создаём новую device session соответствующего user. Если не связан — создаём `users` и `steam_links` в одной транзакции.

### Link Steam к уже существующему user

Требуется действующая сессия и свежая повторная аутентификация. После проверки:

- если SteamID свободен — привязать;
- если уже принадлежит этому user — идемпотентный успех;
- если принадлежит другому user — конфликт, ничего не перемещать;
- не объединять аккаунты автоматически.

Уникальные ограничения БД — последняя защита от гонки двух callback.

## 4. Конфликт аккаунтов

Не раскрывайте лишнюю информацию: сообщение «Этот Steam-аккаунт уже используется» достаточно. Не показывайте email, имя или watchlist другого пользователя.

Процесс восстановления/merge — отдельная чувствительная функция с аудитом и дополнительным доказательством владения. Для MVP лучше направить в поддержку, чем автоматически переносить данные.

## 5. Приватность профессиональных и обычных игроков

Про-матчевые данные и персональная учётная запись приложения могут пересекаться, но не должны автоматически сливаться в публичный профиль.

Правила:

- связанный SteamID не означает согласия показать аккаунт пользователя публично;
- watchlist приватен по умолчанию;
- push preferences приватны;
- аналитика поведения пользователя отделена от публичных игровых данных;
- удаление app-аккаунта не требует удалить объективную запись профессионального матча, но должно убрать личную связь и настройки согласно политике.

## 6. Provider key

Ключ Steam Web API:

- хранится в secret manager backend;
- не попадает в OpenAPI, Expo env или crash reports;
- передаётся adapter только при server-side запросе;
- имеет отдельные значения/политику для окружений, если возможно;
- вращается при подозрении на утечку.

Mobile всегда обращается к нашему backend, а не к protected Steam API напрямую.

## 7. Кэш и отказ provider

Профильный adapter возвращает нормализованное состояние:

```ts
type SteamProfileResult =
  | { status: 'available'; displayName: string; avatarUrl?: string }
  | { status: 'private' }
  | { status: 'not-found' }
  | { status: 'temporarily-unavailable'; retryAfterSeconds?: number };
```

Не превращайте private profile в «ошибку пользователя». Интерфейс показывает нейтральную заглушку. Старый кэш можно показать с `fetchedAt`, если политика свежести это допускает.

## 8. Настройки и согласие

Экран аккаунта объясняет:

- какой Steam account связан;
- какие данные используются;
- как отвязать/удалить аккаунт;
- что произойдёт с watchlist и push;
- где находится privacy policy;
- как запросить экспорт/удаление данных, если это требуется вашей юрисдикцией.

Правовые требования зависят от стран выпуска и меняются; перед production-релизом нужен профильный юридический review, а не догадка из курса.

## 9. Упражнение

Напишите транзакционные тесты:

1. новый SteamID создаёт ровно одного user;
2. повторный login на том же SteamID не создаёт user заново;
3. два параллельных callback не обходят unique constraint;
4. конфликт не раскрывает владельца;
5. provider profile failure не отменяет подтверждённый login;
6. private profile отображается без ошибки.
