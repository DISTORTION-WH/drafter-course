## 1. Продукт и границы MVP

### 1.1. Что мы создаём

Продукт состоит минимум из четырёх систем:

1. Сборщик данных Dota 2.
2. Хранилище и аналитический движок.
3. Backend API на Node.js.
4. Мобильное приложение на React Native.

Главная техническая сложность находится не в мобильных экранах, а в стабильном получении, очистке, связывании и обновлении данных. Поэтому первый технический этап проекта — проверка источников данных, а не разработка красивого интерфейса.

### 1.2. Два возможных направления

#### Профессиональная сцена

Пользователь смотрит:

- турниры и расписание;
- команды и исторические составы;
- статистику профессиональных игроков;
- драфты;
- форму команд;
- мету текущего патча;
- сигнатурных героев;
- контрпики и пары героев;
- результаты матчей;
- графики золота и опыта;
- тайминги предметов и игровых объектов.

Целевая аудитория: продвинутые зрители, игроки, комментаторы, контент-мейкеры, аналитики и тренеры.

#### Анализ личных матчей

Пользователь связывает Steam-профиль и получает:

- историю собственных матчей;
- статистику по героям и ролям;
- прогресс;
- сравнение с профессиональными игроками;
- анализ replay;
- персональные рекомендации.

Это отдельное продуктовое направление: у него другие требования к авторизации, приватности, данным и аналитике.

### 1.3. Выбранный фокус

Первая версия посвящена профессиональной сцене. Личные профили добавляются позже отдельным модулем.

Краткое позиционирование MVP:

> Мобильная аналитика профессиональных матчей, игроков, команд, драфтов и текущей меты Dota 2 для продвинутых зрителей и игроков.

### 1.4. Обязательные функции MVP

#### Главная

- текущие, недавние и ближайшие матчи;
- крупные активные турниры;
- основные изменения меты;
- матчи отслеживаемых команд.

#### Список матчей

- фильтр по турниру, патчу, дате, региону и команде;
- статусы: запланирован, идёт, завершён, отменён;
- счёт серии;
- время начала;
- отображение свежести данных.

#### Детали матча

- Radiant и Dire;
- результат и длительность;
- драфт;
- статистика десяти игроков;
- K/D/A, GPM, XPM, last hits, урон;
- предметы;
- графики преимущества, если источник предоставляет данные;
- ключевые события и игровые объекты, если доступны.

#### Команды

- название, логотип и регион;
- текущий и исторические составы;
- последние матчи;
- форма за 5, 10 и 20 игр;
- предпочтения в драфте;
- статистика по патчам и сторонам карты.

#### Профессиональные игроки

- никнейм и роль;
- текущая команда;
- история команд;
- последние матчи;
- герои;
- форма;
- статистика по патчам;
- сравнение с игроками той же роли.

#### Мета

- pick rate;
- ban rate;
- contest rate;
- win rate;
- этапы драфта;
- Radiant/Dire;
- роли;
- пары и контрпики;
- фильтры по патчу, периоду, региону и уровню турнира.

#### Поиск и избранное

- поиск по игроку, команде, турниру, герою и ID матча;
- отслеживание команд и игроков;
- уведомление о матче и результате.

### 1.5. Что намеренно не входит в MVP

- собственный replay-парсер;
- live-предсказания;
- нейросетевой анализ драфта;
- AI-тренер;
- социальная сеть и чат;
- функции ставок;
- Kubernetes и Kafka;
- сложная микросервисная архитектура;
- полноценная web-версия для пользователей.

### 1.6. Проверяемая ценность MVP

Пользователь должен суметь:

1. Найти ближайший профессиональный матч.
2. Открыть завершённую игру и изучить драфт и статистику.
3. Посмотреть текущий состав и форму команды.
4. Посмотреть мету текущего патча.
5. Добавить команду в избранное.
6. Получить уведомление о начале её следующего матча.

Если этот сценарий не работает целиком, MVP ещё не готов.

## 2. Источники данных и архитектура

### 2.1. Источники данных

Одного API для полного продукта недостаточно.

| Категория | Основной вариант на старте | Зачем нужен |
|---|---|---|
| Базовые матчи и профили | Valve / OpenDota | Результаты, игроки, герои, длительность |
| Расширенная статистика | OpenDota / STRATZ | Драфты, графики, тимфайты, варды, события |
| Профессиональные матчи | OpenDota / STRATZ | История профессиональных игр |
| Турниры и серии | Лицензированный esports API | BO3/BO5, расписание, переносы, standings |
| Команды и составы | Esports API + собственная сверка | Историческая принадлежность игроков |
| Патчи и константы | Valve / OpenDota constants | Герои, предметы, патчи и игровые режимы |
| Детальный replay | Внешние parsed-данные, позднее Clarity | Координаты, combat log, события и heatmap |

Условия использования и лимиты каждого источника необходимо проверять перед коммерческим запуском. Нельзя считать, что лицензия исходного кода API автоматически даёт право коммерчески перераспространять все данные.

### 2.2. Правильная граница внешних API

Мобильное приложение никогда не обращается напрямую к Valve, OpenDota или STRATZ.

Неправильная схема:

```text
React Native → OpenDota
```

Проблемы такой схемы:

- ключи и лимиты невозможно нормально контролировать;
- мобильное приложение зависит от формата чужого API;
- сложно объединить несколько источников;
- пользователь видит ошибки и задержки провайдера;
- нельзя стабильно пересчитывать историческую статистику.

Правильная схема:

```text
Внешние API → фоновые workers → ваша база данных
React Native → ваш Node.js API → ваша база данных
```

### 2.3. Слои системы

#### Provider adapters

Для каждого внешнего источника создаётся отдельный адаптер:

- Valve adapter;
- OpenDota adapter;
- STRATZ adapter;
- Tournament provider adapter.

Адаптер знает формат конкретного API и превращает его в общий внутренний формат приложения.

#### Raw archive

Исходные ответы сохраняются без изменения. Это позволяет:

- повторно обработать данные после исправления ошибки;
- не расходовать API-квоту второй раз;
- расследовать расхождения;
- перенести данные в новую схему;
- пересчитать аналитику.

Маленькая metadata хранится в PostgreSQL, большие ответы и replay-файлы — в S3-совместимом object storage.

#### Normalizer

Normalizer:

- приводит даты к UTC;
- связывает ID игроков и команд;
- определяет патч;
- преобразует поля внешнего API во внутреннюю модель;
- оценивает полноту матча;
- сохраняет происхождение данных.

#### PostgreSQL

Основное хранилище:

- матчи;
- команды;
- игроки;
- составы;
- турниры;
- пользователи;
- избранное;
- агрегаты MVP.

#### Redis и очередь

Redis применяется для:

- кэша API;
- очередей BullMQ;
- блокировок повторной обработки;
- временного хранения quota state.

#### Analytics workers

Отдельные фоновые задачи пересчитывают:

- мету;
- форму команды;
- форму игрока;
- пары и контрпики;
- тренды;
- материализованные представления.

#### Replay parser

Добавляется после MVP как отдельный Java-сервис на базе Clarity. Ошибка parser не должна делать базовые сведения о матче недоступными.

### 2.4. Жизненный цикл матча

```text
discovered
→ details_pending
→ details_received
→ normalized
→ enrichment_pending
→ complete
→ replay_pending
→ replay_parsed
```

Для ошибки используются `failed` и причина ошибки. Любую job можно безопасно запустить повторно.

### 2.5. Idempotency

Idempotency означает, что повторное выполнение операции не создаёт дубликаты и не портит данные.

Пример ключа:

```text
opendota:match:8123456789:details:v3
```

Механизмы:

- уникальные ограничения БД;
- `upsert`;
- hash содержимого;
- provider update timestamp;
- транзакции;
- блокировка одновременно запущенных одинаковых jobs.

### 2.6. Reconciliation

Данные часто появляются частями. Поэтому недавние матчи периодически проверяются снова:

- результат мог появиться раньше полной статистики;
- replay может стать доступен позже;
- состав или серия могут быть исправлены;
- матч может быть перенесён или отменён;
- внешний источник может исправить ошибку.

Интервалы обновления задаются конфигурацией и учитывают лимит конкретного API.

### 2.7. Работа с лимитами

Quota manager должен поддерживать:

- отдельные лимиты на каждый источник;
- ограничение частоты;
- обработку HTTP `429`;
- exponential backoff;
- случайный jitter;
- circuit breaker;
- приоритетные очереди;
- мониторинг оставшейся квоты.

Приоритет получают активные турниры, недавно завершённые матчи и команды из пользовательского избранного. Исторический backfill выполняется с низким приоритетом.

### 3.5. Важные правила модели данных

#### История составов

Недостаточно хранить только текущую команду игрока. Для каждого матча нужен состав, действовавший именно в момент матча.

#### Идентификаторы

У одного игрока могут быть разные ID у Valve, OpenDota, STRATZ и турнирного провайдера. Для этого нужна отдельная таблица соответствий.

#### SteamID64

Все 64-битные ID передаются через JSON строками. JavaScript `number` не гарантирует точное представление любого 64-битного целого.

#### Время

Сервер и БД хранят время в UTC. Мобильное приложение отображает его в локальном часовом поясе пользователя.

#### Происхождение

Важные записи содержат:

- источник;
- время загрузки;
- время обновления у источника;
- версию схемы;
- степень полноты;
- parser version для replay data.

## 4. Аналитика, качество и план разработки

### 4.1. Базовые метрики

```text
Pick rate = число пиков / число драфтов
Ban rate = число банов / число драфтов
Contest rate = (пики + баны) / число драфтов
Win rate = победы героя / игры героя
```

Каждая метрика сопровождается:

- патчем;
- периодом;
- числом матчей;
- фильтрами;
- временем обновления;
- версией формулы.

### 4.2. Статистическая корректность

Простой процент побед может вводить в заблуждение. Поэтому нужны:

- sample size;
- минимальный порог матчей;
- Wilson interval;
- Bayesian shrinkage для маленьких выборок;
- отметка «недостаточно данных»;
- сравнение только одинаковых патчей и временных окон.

Синергия и контрпики являются статистическими связями, а не доказанными причинами победы.

### 4.3. Форма игрока

Окна: 5, 10, 20, 50 матчей и текущий патч.

Показатели:

- KDA;
- GPM/XPM;
- last hits и net worth на фиксированной минуте;
- урон;
- участие в убийствах;
- смертность;
- hero pool;
- результаты по ролям.

Carry и support нельзя сравнивать по абсолютному GPM. Показатели нормализуются по роли, герою, патчу, длительности и уровню соперника.

### 4.4. Форма команды

- win rate;
- Radiant/Dire;
- длительность побед и поражений;
- first blood;
- первый Roshan;
- тайминги башен;
- преимущество на 10/15/20 минуте;
- comeback и throw indicators;
- темп ключевых предметов;
- hero pool;
- first-phase picks;
- стабильность состава.

### 4.5. Предсказания

Не входят в MVP. После накопления данных можно начать с logistic regression, Elo/Glicko и gradient boosting.

Обучающая и тестовая выборки делятся по времени. Модель использует только данные, которые существовали до начала предсказываемого матча. Метрики: log loss, Brier score, calibration и дополнительный ROC-AUC.

### 4.6. Тестирование

#### Backend

- unit tests формул и нормализаторов;
- integration tests с настоящими PostgreSQL и Redis через Testcontainers;
- contract fixtures внешних API;
- проверка повторной обработки;
- тесты миграций.

#### Mobile

- component tests;
- loading/error/empty states;
- deep links;
- offline и reconnect;
- разные часовые пояса;
- E2E через Maestro.

#### Data quality

- отсутствие дубликатов;
- валидные игроки и герои;
- согласованный победитель;
- положительная длительность;
- корректные связи series/match;
- воспроизводимые агрегаты;
- измеримая полнота полей.

### 4.7. Наблюдаемость

Собираются:

- provider errors и `429`;
- использование квот;
- ingestion lag;
- data freshness;
- queue depth;
- retries и dead-letter jobs;

### 4.9. Реалистичные сроки

Для команды из 2–4 человек:

Для одного начинающего разработчика курс и создание MVP займут значительно больше времени. Главная цель курса — не скорость, а понимание каждой части и получение работающего вертикального среза.

### 4.10. Основные риски

| Риск | Мера |
|---|---|
| API недоступен | Второй источник и adapter layer |
| Изменились лимиты | Кэш, quota manager, приоритеты |
| Запрещено коммерческое использование | Проверка условий до разработки |
| Неполный матч | Поле completeness и повторная загрузка |
| Игрок сменил команду | Исторические rosters |
| Разные ID | Provider mapping |
| Патч сломал parser | Версионирование и golden replays |
| Маленькая выборка | Интервалы и sample size |
| PostgreSQL перегружен | Материализация, партиции, затем ClickHouse |
| Scope creep | Жёсткие P0/P1/P2 |

### 4.11. Definition of Done MVP

- основные сведения есть минимум у 95–98% выбранных профессиональных матчей;
- ingestion idempotent;
- метрики воспроизводимы;
- cached API p95 укладывается примерно в 300 мс;
- provider outage не ломает чтение сохранённых матчей;
- приложение работает без регистрации;
- deep links и уведомления протестированы;
- backup действительно восстанавливается;
- в приложении отображаются источник, период и свежесть аналитики.

## 6. AWS, публикация и коммерческий запуск

### 6.1. Честный результат курса

Курс должен привести не к набору скопированных фрагментов, а к трём последовательным результатам:

1. **Рабочий MVP** — приложение получает разрешённые данные профессиональных матчей, сохраняет их, считает мету и показывает mobile UI.
2. **Production-сервис** — backend работает в AWS, mobile проходит beta/store release, данные защищены, расходы ограничены, backup восстановлен на учениях.
3. **Коммерчески готовый продукт** — права на используемые данные и изображения подтверждены, premium entitlement проверяется сервером, покупка проходит sandbox, продуктовые метрики и поддержка работают.

Курс не может гарантировать прибыль. Доход зависит от спроса, качества продукта, прав на коммерческое использование данных, маркетинга, конкурентов, цены, региона и исполнения. Проверяемый результат — продукт, который технически и юридически подготовлен к продаже и получил реальную проверку у целевой аудитории.

### 6.2. Коммерческий стоп-кран

До рекламы, платной подписки или sponsorship создаётся `docs/legal/data-rights-register.md`.

Для каждого источника и вида материала записываются:

| Ресурс | Источник | Что используем | Коммерческое право | Атрибуция | Retention | Подтверждение |
|---|---|---|---|---|---|---|
| match facts | provider | IDs, draft, result | verified/pending/denied | ... | ... | URL/договор/email |
| replay | provider | derived combat/positions | ... | ... | ... | ... |
| hero art | правообладатель | icons | ... | ... | ... | ... |
| team logo | команда/provider | image | ... | ... | ... | ... |
| player photo | ... | image | ... | ... | ... | ... |

Статусы `pending` и `denied` блокируют коммерческий release соответствующей функции. Лицензия программного кода не равна праву коммерчески перераспространять данные, логотипы, фотографии или игровые assets.

Steam Web API Terms разрешают использование только в указанных ими границах и могут изменяться или быть прекращены. На 17 июля 2026 условия требуют, среди прочего, конфиденциальности ключа, privacy policy, недопустимости впечатления об endorsement Valve и содержат ограничения использования Steam Data. Приложение не называется официальным продуктом Valve, не копирует Dota 2/Steam logo как собственный бренд и не обещает betting outcome.

Части 18–20 — replay parsing, ClickHouse и ML — не нужны для первого платного MVP. Они добавляются после подтверждения спроса или измеренной технической необходимости.

### 6.4. AWS reference architecture

Production-shaped вариант:

```text
mobile app
   |
Route 53 + ACM HTTPS
   |
Application Load Balancer
   |
ECS Fargate API service -------- CloudWatch
   |
   +------ RDS PostgreSQL
   +------ ElastiCache, только если BullMQ уже нужен
   +------ private S3 artifacts

ECS worker service
   +------ providers/replays
   +------ RDS/outbox
   +------ S3

EventBridge Scheduler
   -> ECS scheduled discovery/reconciliation task

ECR <- GitHub Actions through OIDC
Secrets Manager -> ECS task secrets
CloudFront + private S3 -> support/privacy/account-deletion web pages
```

Infrastructure описывается AWS CDK v2 на TypeScript. Console используется для обучения и диагностики, но production resources воспроизводятся из code.

### 6.5. Два ценовых профиля

#### Pilot

- один production account и отдельный staging environment;
- минимальное число Fargate tasks;
- RDS Single-AZ с PITR и проверенным restore;
- PostgreSQL outbox вместо Redis, если throughput позволяет;
- ограниченные логи/retention;
- feature flags выключают дорогие replay/ML;
- принято окно возможного простоя.

#### Standard

- отдельные AWS accounts для production и non-production;
- ECS tasks в private subnets минимум двух AZ;
- RDS Multi-AZ;
- ElastiCache с TLS/RBAC, если очередь критична;
- NAT/VPC endpoints по рассчитанной модели;
- WAF только после threat/cost decision;
- регулярные restore и incident drills.

Переход определяется SLO, риском и revenue, а не желанием выглядеть «enterprise». Текущая стоимость каждый раз рассчитывается в AWS Pricing Calculator; числа из курса не являются прайс-листом.

### 6.6. Выбранная стартовая монетизация

Основной учебный вариант — freemium subscription:

#### Бесплатно

- расписание и результаты;
- базовые детали матча;
- ограниченный текущий meta view;
- небольшое число watchlist subscriptions;
- базовые уведомления.

#### Premium

- расширенные фильтры и длинные периоды;
- сравнение команд/игроков;
- больше watchlists и настраиваемых уведомлений;
- сохранённые аналитические views;
- advanced draft/meta reports;
- экспорт только при наличии права перераспространять соответствующие данные.

Фактический результат матча, account deletion, privacy controls и уже приобретённые права пользователя не прячутся за paywall.

На iOS и Android доступ к цифровым функциям продаётся согласно актуальным правилам соответствующего store. Исключения, alternative billing и внешние ссылки зависят от storefront/программы и меняются; их нельзя переносить из статьи или другого приложения без повторной проверки.

### 6.7. Entitlement, а не флаг в телефоне

```text
store purchase
-> signed/store purchase token
-> secure backend verification
-> immutable billing event
-> entitlement state
-> API authorization for premium capability
-> mobile renders allowed state
```

Mobile не сам решает, что пользователь premium. Backend проверяет Apple/Google status, обрабатывает renewal, grace period, cancellation, refund, billing retry и duplicate notifications. Webhooks/notifications являются сигналом; authoritative status при необходимости запрашивается у store API.

### 6.8. Бизнес-метрики

До запуска определяются:

- activation: пользователь получил первый полезный meta insight;
- D1/D7/D30 retention;
- weekly active users;
- free-to-trial и trial-to-paid conversion;
- monthly recurring revenue;
- voluntary/involuntary churn;
- refund rate;
- support requests;
- gross revenue minus store fee/tax/provider/AWS/support cost;
- contribution margin;
- cost per active/free/paid user.

Event tracking проходит privacy review. Нельзя собирать «всё на будущее».

### 6.9. Go-to-market

До разработки premium проводится 10–20 интервью с представителями выбранного сегмента: аналитики, тренеры, комментаторы, контент-мейкеры или продвинутые зрители. Проверяется одна проблема, а не вопрос «нравится ли идея».

Первый запуск:

```text
landing page + waitlist
-> 10–30 закрытых testers
-> weekly interviews/support
-> исправление activation/retention
-> store beta
-> one paid offer
-> measured acquisition experiments
```

Спам, покупка отзывов, скрытая реклама, использование чужих сообществ без правил и ложные claims запрещены.
