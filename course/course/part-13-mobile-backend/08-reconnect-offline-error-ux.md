# Глава 8. Reconnect, offline и error UX

## 1. Offline — не одна ошибка

Для пользователя одинаково выглядят разные причины:

- телефон действительно без сети;
- Wi-Fi есть, но нет интернета;
- DNS не нашёл домен;
- TLS-сертификат неверен;
- backend недоступен;
- запрос превысил timeout;
- API вернул 503.

Приложение не всегда способно точно определить причину. Поэтому обещайте только то, что знаете: «Не удалось связаться с сервером», а не «У вас выключен Wi-Fi», если это не подтверждено.

## 2. Подключаем состояние сети

TanStack Query можно связать с поддерживаемым Expo/React Native модулем состояния сети через `onlineManager`. Конкретный адаптер зависит от зафиксированных версий, но принцип такой:

```ts
onlineManager.setEventListener((setOnline) => {
  const unsubscribe = networkModule.subscribe((state) => {
    setOnline(state.isInternetReachable !== false);
  });

  return unsubscribe;
});
```

Не считайте `isConnected: true` гарантией доступа к API. Это лишь сигнал для разумного поведения query.

Аналогично `focusManager` связывается с `AppState`, чтобы при возвращении приложения на экран устаревшие данные могли обновиться.

## 3. Кэш как read-only fallback

Стартовая offline-стратегия:

```text
есть кэш + сеть пропала -> показываем кэш с отметкой «данные могут быть устаревшими»
нет кэша + сеть пропала -> offline empty state с кнопкой повторить
mutation без сети       -> не обещаем сохранение, просим повторить
сеть вернулась          -> активные устаревшие query обновляются
```

Не создавайте очередь offline-mutations, пока не определены идемпотентность, срок жизни, порядок выполнения, конфликт и UX отмены. Для первой версии анализатора read-only offline cache достаточно.

## 4. Матрица состояний компонента

Создайте общий `QueryBoundary`, но не прячьте в нём смысл каждого экрана:

| Данные | Ошибка | Fetching | UI |
|---|---|---|---|
| нет | нет | да | skeleton |
| нет | есть | нет | полноэкранная ошибка + retry |
| есть | нет | нет | контент |
| есть | нет | да | контент + тихий индикатор |
| есть | есть | нет | старый контент + warning banner |
| пустой массив | нет | нет | product empty state |

Пустой список — успешный ответ, а не ошибка.

## 5. Обновление по pull-to-refresh

```tsx
<FlatList
  refreshControl={
    <RefreshControl
      refreshing={query.isRefetching && !query.isFetchingNextPage}
      onRefresh={() => void query.refetch()}
    />
  }
/>
```

Для infinite query уточните продуктовую семантику: обычно refresh перечитывает цепочку с начала, а не только последнюю страницу. Не запускайте refresh одновременно с загрузкой следующей страницы.

## 6. Error UX по статусу

Примеры:

```ts
export function getErrorPresentation(error: unknown) {
  if (!(error instanceof ApiError)) {
    return { title: 'Нет связи с сервером', retryable: true };
  }

  if (error.status === 404) {
    return { title: 'Данные не найдены', retryable: false };
  }

  if (error.status === 429) {
    return { title: 'Слишком много запросов', retryable: true };
  }

  return {
    title: 'Не удалось загрузить данные',
    retryable: error.status >= 500,
    requestId: error.requestId,
  };
}
```

Показывайте `requestId` в раскрываемых технических деталях или при копировании обращения, а не как главный заголовок.

## 7. Reconnect без шторма

После возвращения сети десятки устаревших query могут одновременно обратиться к API. Настройте:

- разумный `staleTime`;
- ограниченный retry;
- серверный rate limit;
- дедупликацию одинаковых query библиотекой;
- jitter/backoff для фоновых процессов;
- приоритет активных экранов над невидимыми данными.

## 8. Тестовые сценарии

Проверьте на development build:

1. открыть список, включить авиарежим, вернуться в приложение;
2. запустить без кэша и без сети;
3. потерять сеть во время следующей страницы;
4. вернуть сеть и убедиться, что нет десятков одинаковых запросов;
5. получить 429 с `Retry-After`;
6. получить 500 с `requestId`;
7. свернуть приложение на 10 минут и вернуть;
8. сменить фильтр во время медленного запроса.
