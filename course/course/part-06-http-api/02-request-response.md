# Глава 2. HTTP-запрос и HTTP-ответ

[← Глава 1](01-client-server-url.md) · [Оглавление](README.md) · [Глава 3 →](03-json-unknown-validation.md)

## Модель обмена

HTTP-сообщение логически состоит из start line, headers и необязательного body.

```text
GET /api/matches/123 HTTP/1.1
Accept: application/json

```

Ответ:

```text
HTTP/1.1 200 OK
Content-Type: application/json

{"match_id":123}
```

`fetch` скрывает формат провода, но понятия остаются.

## Методы

- `GET` — прочитать;
- `POST` — создать ресурс или запустить команду;
- `PUT` — заменить представление целиком;
- `PATCH` — частично изменить;
- `DELETE` — удалить.

Получение матча — `GET`. Повторный безопасный `GET` не должен сам создавать новые бизнес-эффекты. Это свойство называют safe. Повторение запроса с тем же результатом состояния называют idempotent. Эти понятия важны для retry.

## Headers

Headers — метаданные, не основное содержимое:

```ts
const headers = new Headers({
  accept: 'application/json',
  'user-agent': 'dota-analyzer-course/0.1',
});
```

`Accept` сообщает желаемый тип ответа. `Content-Type` описывает формат отправленного body. Для `GET` без body ставить `Content-Type: application/json` обычно бессмысленно.

Не выводите в log значения `Authorization`, cookies и API keys.

## Status code — это часть данных

Основные группы:

- `2xx` — запрос обработан успешно;
- `3xx` — перенаправление;
- `4xx` — запрос клиента нельзя выполнить в текущем виде;
- `5xx` — сервер не выполнил корректный запрос.

Важные коды для клиента данных:

- `200` — ответ есть;
- `400` — неверные параметры;
- `401` — нет подходящей аутентификации;
- `403` — доступ запрещён;
- `404` — ресурс не найден;
- `408` — сервер сообщает timeout запроса;
- `429` — превышено ограничение;
- `500`, `502`, `503`, `504` — временная или постоянная серверная проблема.

## `fetch` не отклоняет Promise на каждый 4xx/5xx

Сетевой запрос может успешно получить ответ `500`. С точки зрения транспорта Promise выполнен. Поэтому нужна явная проверка:

```ts
const response = await fetch(url);

if (!response.ok) {
  throw new Error(`HTTP ${response.status} ${response.statusText}`);
}
```

`response.ok` истинно для диапазона `200–299`.

## Body — поток, читаемый один раз

```ts
const response = await fetch(url);
const text = await response.text();
```

После чтения `text()` нельзя просто вызвать `json()` на том же body: поток уже использован. Для диагностики удобно сначала прочитать текст, затем разобрать JSON:

```ts
const bodyText = await response.text();
const body: unknown = JSON.parse(bodyText);
```

При больших payload тело нельзя бездумно держать в памяти, но для одного матча этот шаг приемлем. Ограничение размера мы добавим на серверной границе позже.

## Полезные response headers

- `content-type` — ожидаем ли JSON;
- `retry-after` — когда повторить запрос после ограничения;
- `etag` и `last-modified` — условный cache;
- provider-specific headers квоты — только если провайдер документирует их.

Не проектируйте приложение вокруг недокументированного заголовка.

## Практика

Для каждого сценария ответьте: retry или нет?

1. `400` из-за неправильного match ID.
2. `404` для матча.
3. `429` и `Retry-After: 10`.
4. `503` без body.
5. DNS не нашёл host.

Ожидаемое рассуждение: 1 и 2 не исправятся немедленным повтором; 3 — повтор после указанной паузы; 4 и 5 иногда временные, значит возможен ограниченный retry.
