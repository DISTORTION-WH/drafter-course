# 11. Разбор эталонного проекта

Эталон находится в [examples/dota-history-cli](examples/dota-history-cli).

Он специально не использует внешние библиотеки. Сейчас важно увидеть механизм Node.js и JavaScript без скрывающих его framework-абстракций.

## 1. Карта проекта

```text
data/matches.json
        │
        ▼
src/io/read-json.js
        │ unknown
        ▼
src/domain/validation.js
        │ корректная история
        ▼
src/domain/history-analytics.js
        │ report
        ▼
src/presentation/print-history-report.js
```

`src/index.js` координирует движение между слоями.

## 2. Назначение файлов

### `data/matches.json`

Три вымышленных профессиональных матча. Некоторые игроки и герои повторяются, поэтому можно проверить историю, а не только один матч.

### `src/io/read-json.js`

Инфраструктурный слой:

- асинхронно читает текст;
- разбирает JSON;
- добавляет контекст к ошибкам.

Он ничего не знает о Radiant, Dire или героях.

### `src/domain/validation.js`

Описывает инварианты нашей предметной области:

- матч завершён;
- игроков 10;
- стороны распределены 5 на 5;
- показатели неотрицательны;
- ID не повторяются внутри матча.

### `src/domain/history-analytics.js`

Содержит чистые расчёты:

- агрегирование героев через `Map`;
- уникальные account ID через `Set`;
- общие суммы и средние;
- короткие match summaries;
- детерминированную сортировку.

### `src/presentation/print-history-report.js`

Преобразует report в строки CLI. Если завтра появится REST API, domain-расчёты менять не потребуется.

### `src/index.js`

Composition root — место, где приложение соединяется:

```js
const rawData = await readJsonFile(inputPath);
const report = analyzeMatchHistory(rawData);
printHistoryReport(report);
```

## 3. Направление зависимостей

Presentation знает форму отчёта. Domain знает форму матчей. I/O не знает domain-правил.

```text
index
├── io
├── domain
└── presentation
```

Domain не импортирует I/O или presentation. Это важно: аналитика не должна зависеть от того, пришли матчи из файла, PostgreSQL или HTTP.

## 4. Поток одной переменной

Проследим данные:

```js
const rawData = await readJsonFile(inputPath);
```

`rawData` — результат внешнего источника. Мы ещё не должны слепо доверять его форме.

```js
const report = analyzeMatchHistory(rawData);
```

Публичная функция сначала выполняет validation, затем возвращает новый объект. Исходные данные не изменяются.

```js
printHistoryReport(report);
```

Printer не пересчитывает статистику. Он только выбирает порядок и формат строк.

## 5. Почему `Map` внутри, а массив снаружи

Во время группировки нужен быстрый доступ по герою:

```js
statsByHero.get(player.hero)
```

Поэтому внутри используется `Map`.

Но JSON и UI удобнее получают обычный массив:

```js
const heroStats = [...statsByHero.values()];
```

Внутренняя структура выбирается для вычисления, внешняя — для удобного обмена.

## 6. Почему среднее округляется в конце

Правильно:

```js
roundToTwoDigits(totalKills / games)
```

Нежелательно округлять каждое сложение. Раннее округление на большой истории накапливает погрешность. Храним точные суммы и форматируем конечный показатель.

## 7. Зачем проверять неизменность данных

Тест сохраняет копию входа:

```js
const before = structuredClone(matches);
analyzeMatchHistory(matches);
assert.deepEqual(matches, before);
```

Так мы защищаемся от случайного `sort`, `reverse` или изменения вложенного объекта. Чистая аналитика может безопасно использоваться несколькими экранами.

## 8. Как читать проект новичку

Рекомендуемый порядок:

1. `data/matches.json` — увидеть форму входа;
2. `src/index.js` — понять общий сценарий;
3. `src/io/read-json.js` — изучить границу файла;
4. `src/domain/validation.js` — увидеть правила;
5. `src/domain/history-analytics.js` — пройти расчёты с отладчиком;
6. `src/presentation/print-history-report.js` — увидеть вывод;
7. `test/` — прочитать примеры ожидаемого поведения.

Не пытайтесь запомнить проект. Поставьте breakpoint, следите за `rawData`, `Map`, `Set` и итоговым `report`.

## 9. Эксперименты

В отдельной копии проекта:

1. добавьте четвёртый матч;
2. замените героя у одного игрока и проследите статистику;
3. добавьте второго stand-in и проверьте `uniquePlayers`;
4. сломайте `radiantWin` строкой `"true"`;
5. удалите игрока;
6. добавьте вывод трёх героев с лучшим win rate при минимум двух играх;
7. добавьте аргумент `--top=3` без сторонней CLI-библиотеки.

После каждого изменения сначала сформулируйте ожидаемый результат, затем запускайте тест.

## 10. Что вы уже умеете после части 3

- передавать функции как значения;
- строить цепочки `map`, `filter`, `reduce` и `flatMap`;
- избегать ненужных мутаций;
- группировать через `Map`;
- считать уникальные значения через `Set`;
- понимать event loop на практическом уровне;
- использовать Promise и `async/await`;
- читать JSON-файлы;
- разделять I/O, validation, analytics и presentation;
- тестировать асинхронный и чистый код.

## 11. Переход к части 4

JavaScript запускает код, но не заставляет заранее доказать форму данных. Следующая часть вводит TypeScript:

- базовые типы;
- `type` и `interface`;
- union и literal types;
- `unknown` вместо опасного `any`;
- narrowing;
- generics;
- типизированные ошибки и Result-подход;
- перенос этого CLI с JavaScript на TypeScript.

Именно TypeScript станет основным языком backend и React Native приложения.
